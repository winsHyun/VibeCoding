# PRD 2단계: 레시피 생성

## 1. 개요

1단계에서 확정한 재료 목록으로 만들 수 있는 레시피를 생성해 보여 준다.

- 사용 모델: `nvidia/nemotron-3-nano-omni-30b-a3b-reasoning:free` (OpenRouter, 대화형 추론 모델)
- 선행 단계: `PRD_step1.md` (확정된 재료 목록을 입력으로 받음)
- 후속 단계: `PRD_step3.md` (생성된 레시피 저장, 프로필 정보를 프롬프트에 반영)

## 2. 모델 특성 (사전 테스트 결과, 2026-10-26)

- 한국어 질문에 한국어로 정확히 답했다("대한민국의 수도는 서울입니다.", 약 0.3~0.6초, 비용 0).
- **추론 모델**이다. 답하기 전에 내부 추론을 하며, 추론 내용은 `message.reasoning`, 최종 답은 `message.content`에 따로 온다. 앱은 `content`만 쓴다. 추론 토큰도 출력 토큰으로 계산되므로 `max_tokens`를 넉넉히 잡아야 답이 잘리지 않는다.
- 무료 모델이라 서버 과부하 오류가 날 수 있다(테스트 중 `ResourceExhausted: Worker local total request limit reached` 502 오류 확인).

## 3. 목표 / 비목표

**목표**
- 확정된 재료로 만들 수 있는 레시피 3개를 추천한다.
- 레시피마다 필요한 재료 중 "가진 재료"와 "추가로 필요한 재료"를 구분해 보여 준다.
- 결과를 정해진 JSON 구조로 받아 화면에 일정한 형식으로 그린다.

**비목표**
- 레시피 이미지 생성
- 영양 성분의 정확한 계산 (대략적인 칼로리만 참고로 표시)
- 스트리밍 출력 (1차 버전은 완성된 응답을 한 번에 표시)

## 4. 사용자 흐름

1. 1단계에서 "재료 확정"을 누르면 레시피 화면으로 넘어간다.
2. 선택 옵션을 고른다: 요리 시간(제한 없음/15분/30분/60분), 난이도(쉬움/보통/어려움), 인분(1~4).
3. "레시피 추천"을 누르면 로딩 표시("레시피를 고민하는 중…") 후 레시피 카드 3개가 나온다.
4. 카드를 누르면 재료, 단계별 조리법, 팁이 펼쳐진다.
5. "다시 추천"으로 다른 레시피 3개를 받는다(이전 레시피 이름을 프롬프트에 넣어 중복을 피함).
6. 3단계가 구현되면 카드에 "저장" 버튼이 생긴다.

## 5. 기능 요구사항

| ID | 요구사항 |
|---|---|
| F2-1 | 입력: 재료 이름 배열(1단계 결과), 옵션(시간·난이도·인분), 제외할 레시피 이름 배열(다시 추천용). 3단계 이후에는 프로필 정보(알레르기, 식단 제한, 선호)가 추가된다. |
| F2-2 | 서버가 시스템 프롬프트 + 사용자 프롬프트를 만들어 OpenRouter `chat/completions`를 호출한다. |
| F2-3 | 모델에게 아래 6장의 JSON 구조만 출력하라고 지시한다. 응답 `content`에서 첫 `{`부터 마지막 `}`까지 잘라 파싱하고(코드 블록 표시 등 제거), 스키마를 검증한다. |
| F2-4 | 파싱·검증에 실패하면 "JSON 형식이 잘못되었다"는 메시지를 덧붙여 1회 다시 요청한다. 그래도 실패하면 오류를 반환한다. |
| F2-5 | 레시피 재료마다 `owned`(보유 여부)를 서버에서 다시 계산한다. 1단계 재료 목록과 이름을 비교하며, 모델 판단을 그대로 믿지 않는다. |
| F2-6 | 기본 양념(소금, 후추, 식용유, 간장, 설탕, 물)은 보유한 것으로 간주한다. 목록은 설정값으로 둔다. |
| F2-7 | 요청 파라미터: `max_tokens` 4000, `temperature` 0.7, `include_reasoning: false`(추론 내용을 응답에서 제외). 이 모델은 `response_format`을 지원하지 않는다(OpenRouter 지원 파라미터 목록 확인, 2026-10-26). 그래서 JSON 형식은 프롬프트 지시 + F2-3/F2-4로 보장한다. |

## 6. 레시피 데이터 구조

```json
{
  "recipes": [
    {
      "title": "달걀 양파 볶음밥",
      "summary": "남은 밥과 달걀로 10분 만에 만드는 한 그릇 요리",
      "cookTimeMinutes": 15,
      "difficulty": "easy",
      "servings": 2,
      "caloriesPerServing": 520,
      "ingredients": [
        { "name": "달걀", "amount": "2개", "owned": true },
        { "name": "대파", "amount": "1/2대", "owned": false }
      ],
      "steps": ["양파를 잘게 썬다.", "팬에 기름을 두르고 달걀을 스크램블한다."],
      "tips": "찬밥을 쓰면 더 고슬고슬하다."
    }
  ]
}
```

- `difficulty`: `easy` | `medium` | `hard`
- `recipes`는 정확히 3개. 각 레시피는 1단계 재료를 최소 2개 이상 써야 한다(서버에서 검증하고, 못 지킨 레시피는 화면에서 아래로 정렬).

## 7. 프롬프트 설계 (초안)

**시스템 프롬프트**
```
너는 한국 가정 요리 전문가다. 사용자가 가진 재료를 최대한 활용하는 현실적인 레시피를 추천한다.
반드시 지정된 JSON 형식으로만 답하고, JSON 밖에 다른 글을 쓰지 마라.
모든 텍스트는 한국어로 쓴다.
```

**사용자 프롬프트**
```
가진 재료: {재료 목록}
조건: 조리 시간 {시간} 이내, 난이도 {난이도}, {인분}인분
제외할 레시피: {이전 레시피 이름}
[3단계 이후] 알레르기: {알레르기} / 식단 제한: {식단} / 선호: {선호}
가진 재료를 최대한 많이 쓰고, 추가 재료는 최소화한 레시피 3개를 아래 JSON 형식으로 답해라.
{6장의 JSON 예시}
```

## 8. API 명세

`POST /api/recipes`

요청:
```json
{
  "ingredients": ["달걀", "양파", "두부"],
  "options": { "maxCookTimeMinutes": 30, "difficulty": "easy", "servings": 2 },
  "excludeTitles": []
}
```

응답 200: 6장의 구조 + `elapsedMs`

오류 코드: 1단계와 같은 `RATE_LIMITED`, `UPSTREAM_ERROR`에 다음을 추가한다.
- `INVALID_INPUT`: 재료 0개 또는 옵션 값 오류
- `INVALID_MODEL_OUTPUT`: 재시도 후에도 JSON 파싱·검증 실패

## 9. 비기능 요구사항

- **응답 시간:** 목표 30초 이내 (추론 모델이라 출력이 길면 느려질 수 있음). 서버의 OpenRouter 요청 타임아웃은 60초로 둔다.
- **재시도:** 429·502는 1단계와 같은 지수 백오프 규칙을 따른다(공통 모듈로 만든다).
- **안전:** 알레르기 정보가 있으면 해당 재료가 레시피에 들어가지 않았는지 서버에서 한 번 더 검사하고, 들어갔으면 경고 표시를 붙인다(3단계와 연동).

## 10. 수용 기준

- [ ] 재료 3개 이상을 넣으면 30초 안에 레시피 카드 3개가 나온다.
- [ ] 모든 카드에 재료(보유/추가 필요 구분), 단계별 조리법, 조리 시간이 표시된다.
- [ ] 같은 재료로 20회 요청했을 때 JSON 파싱 최종 실패율이 5% 미만이다.
- [ ] "다시 추천"을 누르면 이전과 이름이 다른 레시피가 나온다.
- [ ] 모델 응답의 `reasoning` 내용은 화면에 나오지 않는다.

## 11. 구현 상태 (2026-10-26)

- 구현: `src/recipes.js`(프롬프트·JSON 추출·검증·보유 재판정·재요청), `POST /api/recipes`, 레시피 화면(조건 선택, 펼치는 카드, 다른 레시피 추천).
- `npm test`: 응답 처리 로직 11개 테스트 통과. 가짜 모델 응답으로 JSON 오류 재요청, 답 잘림 재요청, 보유 판정, 정렬을 검증했다.
- **실제 모델 검증은 아직 못 했다.** 구현 당일 OpenRouter 하루 무료 한도가 소진되었다. 한도가 초기화되면 `npm run check:recipes -- 20`으로 수용 기준(JSON 최종 실패율 < 5%, 30초 이내)을 확인한다.
- 데모 모드(`npm run demo`)에서는 고정 예시 레시피 6개 중 3개씩 돌려준다. 보유 판정은 실제 로직을 그대로 쓴다.
- 보유 재료 판정은 이름 포함 관계로 하므로 "계란"과 "달걀"처럼 다른 이름의 같은 재료는 구별하지 못한다.

## 12. 리스크

| 리스크 | 대응 |
|---|---|
| 추론 모델이 JSON 대신 설명문을 섞어 씀 | 잘라서 파싱 + 1회 재요청, `response_format` 지원 시 사용 |
| 추론 토큰 때문에 `max_tokens`에 걸려 답이 잘림 | `finish_reason`이 `length`면 `max_tokens`를 늘려 1회 재요청 |
| 1단계 인식 오류가 레시피 품질로 이어짐 | 1단계 사용자 확인 단계에서 흡수 |
| 무료 모델 과부하(502) | 재시도, 모델 ID를 설정값으로 분리해 교체 가능하게 함 |
